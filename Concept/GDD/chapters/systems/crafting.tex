\section{Crafting Systems}


\subsection{Gear Crafting}

\paragraph{Overview}
The Gear Crafting System combines deterministic player-driven modification (Affixes) with random initial base generation (Implicits). 
Each gear item is defined by its \textbf{Gear Type} (Head, Chest, Leg, Boots, Gloves, Amulet) and can contain:
\begin{itemize}
	\item Up to \textbf{N Implicits} (rolled automatically on creation)
	\item Up to \textbf{M Affixes} (player-crafted and upgradable)\\
\end{itemize}

Each mechanic type has its own input/output schema, cost structure, and scaling formula.
All crafting transactions are atomic (no partial resource loss).\\
Access to specific crafting mechanics (Infuse, Re-Infuse, Tempering, Over-Tempering) is gated by the Crafting Research Tree (see Section~\ref{subsec:research-system}).
Early game only basic recipes are available; advanced mechanics unlock gradually.\\

Ingredients are always Materials (Parts, Remains). 
Currencies are account-wide resources (e.g. Gold, Crystals) and are not stored in the item inventory.

\vspace{0.5em}
\noindent
\textbf{Design Goal:} Create meaningful player agency through controlled randomness and resource-driven progression.
\vspace{1em}

\paragraph{Outcome Modifier Effects}
Depending on rarity/quality and quantity of the used modifier material, the output can be influenced.
This mechanic is intentionally designed as a ``controlled randomness'' lever (not a hard guarantee).

\begin{center}
	\begin{tabular}{|l|l|l|}
		\hline
		\textbf{Parameter} & \textbf{Symbol / Range} & \textbf{Description} \\ \hline
		Tier Boost per Unit & $f_1(q)$ & Adds virtual tier levels to implicits. \\
		Roll Bias per Unit & $f_2(q)$ & Shifts roll toward max value. \\
		Signature Role Shift & $f_3(q)$ & Shifts Signature implicit towards \texttt{Defense/Offense/Utility} (caps apply). \\
		Caps & $\text{cap}_T, \text{cap}_B, \text{cap}_R$ & Hard caps for tier, bias, and role-shift intensity. \\
		Diminishing Curve & $D(q)$ & Function for diminishing returns. \\ \hline
	\end{tabular}
\end{center}

\paragraph{Implicit Pools and Roles}
Implicits are rolled automatically when a base item is created. To preserve archetype identity while still allowing ``weird builds'',
each implicit belongs to:
\begin{itemize}
	\item an \textbf{ImplicitPool} (playstyle): \texttt{Melee} / \texttt{Ranged} / \texttt{Caster} / \texttt{Neutral}
	\item an \textbf{ImplicitRole} (balance tag): \texttt{Defense} / \texttt{Offense} / \texttt{Utility}
\end{itemize}

\noindent
\textbf{Neutral Pool:} generic stats that should be available for all (e.g. Life, Element Resists, Movement Speed, Rarity).
Neutral implicits do \textbf{not} roll on the Signature slot by default.

\paragraph{Signature Implicit (Slot 1)}
The first implicit slot is a \textbf{Signature Implicit} which defines the armor identity.
\begin{itemize}
	\item Signature always rolls from the \textbf{MainPool} of the armor class (no Neutral).
	\item Signature is biased towards \textbf{Defense} by default.
	\item Signature can be influenced via \textbf{Signature Role Shift} (Outcome Modifier), but is always capped.
\end{itemize}

\paragraph{Implicit Count by Base Tier}
\begin{itemize}
	\item \textbf{T1 base:} 1 implicit (Signature only)
	\item \textbf{T2 base:} 2 implicits (Signature + Mixed Slot)
	\item \textbf{T3 base:} 3 implicits (Signature + 2 Mixed Slots)
\end{itemize}

\end{center}

Mixed slots can roll from Main/Secondary/Third pools plus a small Neutral add-on (slot- and GearType-dependent).

\paragraph{Roll Flow (per implicit slot)}
\begin{itemize}
	\item \textbf{Slot 1 (Signature):}
	\begin{enumerate}
		\item Pool = MainPool(ArmorClass) (fixed, no Neutral)
		\item Role = weighted by \texttt{roleWeightsSignature(GearType)} (default Defense-heavy, can be shifted by modifier)
		\item Pick an implicit from the candidate set filtered by \texttt{GearType+Pool+Role}(equal-weighted by default; optional global \texttt{weight} per ImplicitDef).
	\end{enumerate}
	
	\item \textbf{Slot 2 / Slot 3 (Mixed):}
	\begin{enumerate}
		\item Pool = weighted choice from \{Main, Secondary, Third, Neutral\} (slot-dependent weights)
		\item Role = weighted by \texttt{roleWeightsNormal(GearType)}
		\item Pick an implicit from the candidate set filtered by \texttt{GearType+Pool+Role} (equal-weighted by default; optional global \texttt{weight} per ImplicitDef).
	\end{enumerate}
\end{itemize}

\paragraph{Candidate selection}
\noindent
After choosing Pool and Role, an implicit is selected from the candidate list filtered by:
\texttt{pool}, \texttt{role}, and \texttt{allowedGearTypes}.
All candidates are equal-weighted by default (optional global \texttt{weight} per ImplicitDef).

\paragraph{Minimal Data Model (Implicits)}
\begin{itemize}
	\item \textbf{ImplicitDef:} \texttt{id}, \texttt{pool}, \texttt{role}, \texttt{allowedGearTypes} (optional: global \texttt{weight})
	\item \textbf{ArmorClassConfig:} \texttt{mainPool}, \texttt{slot2PoolWeights}, \texttt{slot3PoolWeights}
	\item \textbf{GearTypeConfig:} \texttt{roleWeightsSignature}, \texttt{roleWeightsNormal}, \texttt{neutralWeight(Slot2/Slot3)}
	\item \textbf{OutcomeModifierDef:} \texttt{tierBoost}, \texttt{rollBias}, \texttt{signatureRoleShift} (each with caps + diminishing)
\end{itemize}

\paragraph{Reroll Affix}

\begin{itemize}
	\item Only one slot per item can be rerolled
	\item slot is chosen randomly
	\item Rerolls the Affix effect
	\item no duplicate of existent Affixes
	\item the more Affixes are on the item, the smaller the Reroll-Range of which Affix will be rolled
	\item relativley high base cost, but no Sclaing, since 1 time per item
\end{itemize}

\subsubsection*{General Validation Rules}

\begin{itemize}
	\item Recipes must define $\leq 4$ ingredients and $\leq 1$ booster.
	\item All costs non-negative; zero costs invalid.
	\item ItemBaseDef must specify GearType and AllowedPools.
	\item Atomic transactions: no partial resource consumption.
	\item Rollback mandatory on any failure path.
\end{itemize}

\subsection{Skill Module Crafting}

\paragraph{Overview}
Skill Module Crafting is a \textbf{deterministic} system that creates socketable Skill Modules.
A Skill Module always represents a \textbf{concrete skill} plus a chosen \textbf{SkillTier} and an optional \textbf{DamageType core}.
How the player unlocks skills and FrameTiers is handled by the Research system; this section assumes all unlocked recipes are visible in the Crafting UI.

\paragraph{Definitions}
\begin{itemize}
	\item \textbf{Skill Module (Output):} \texttt{SkillId + SkillTier + CoreType} (as an inventory item).
	\item \textbf{FrameTier:} unlocked via Research (permission gate). The player selects the desired tier via a simple tier slider.
	\item \textbf{CoreType:} defines the damage type conversion and adds the corresponding damage tag automatically.
\end{itemize}

\paragraph{Unlocking}
\begin{itemize}
	\item \textbf{FrameTiers:} unlocked via Research (slider max is capped by the highest unlocked FrameTier).
	\item \textbf{Skill recipes:} unlocked together with the coresponding \textbf{FrameTier}-Research
	\item \textbf{Element Cores:} typically dropped from elites / map rewards (used to enable element conversion and as a ``hint'' for progression).
\end{itemize}

\paragraph{Sequence (UI Flow)}
\begin{enumerate}
	\item Select Skill Recipe (only unlocked skills are craftable).
	\item Select SkillTier via slider (1..max unlocked FrameTier).
	\item Select Core:
	\begin{itemize}
		\item default: BasicCore (Tier1) is used
		\item optional: \textit{Change Core} to an Element Core (if allowed by the selected skill)
	\end{itemize}
	\item UI shows required materials and missing items (craft button becomes green if all requirements are met).
	\item Consume Materials + Currency (atomic transaction) and output the Skill Module.
\end{enumerate}

\subparagraph{Skill Metadata (for UI)}
Each SkillDef defines:
\begin{itemize}
	\item \textbf{PrimaryStat:} the main scaling stat (STR / DEX / CON / INT / WIL).
	\item \textbf{Tags:} one or more tags that describe behaviour and interactions.
\end{itemize}

\paragraph{Core Rules (BasicCore vs Element Core)}
To preserve the story fantasy that every Skill Module consists of \textbf{Core + Frame}, a default core is always present:
\begin{itemize}

	\item If the player selects an \textbf{Element Core} via \textit{Change Core}, the \textbf{250 Gold BasicCore cost is removed}.
	Only the base crafting costs (Parts/Remains/Gold) remain.
\end{itemize}

\subsection{Attunement (Endgame)}

\paragraph{Purpose}

Attunement is an endgame progression system that creates \textbf{meaningful specialization} into either Holy or Daemonic defense while enforcing \textbf{strategic trade-offs} (resistance vs.\ one mythic damage type at the cost of vulnerability to the opposite).
It is designed to:

\begin{itemize}
	\item Provide a \textbf{clear late-game build identity} per hero (Holy-aligned vs.\ Daemonic-aligned), encouraging distinct roster roles rather than a single universal character.
	\item Turn \textbf{Map Consecration / Desecration} into a high-impact endgame decision that alters enemy composition (tags and damage conversion) and thereby increases the chance for \textbf{higher-quality loot} (e.g., \texttt{rarity: mythic}) and improved crafting materials.
	\item Establish a deliberate \textbf{grind loop with variety}: Holy-aligned progress depends on farming Daemonic enemies (and vice versa), ensuring that the optimal path involves alternating content types instead of repeating the same setup indefinitely.
	\item Encourage \textbf{hero rotation} as a core endgame behavior: due to opposing-essence requirements and the vulnerability created by extreme attunement, players are incentivized to swap between specialized heroes rather than continuously pushing only one character.
\end{itemize}

\paragraph{Sequence}

\begin{center}
	\begin{tikzpicture}[node distance=1.2cm]
		\node[draw,rounded corners,fill=gray!15,minimum width=5.5cm] (choosemap) {Select Map \& Choose: Consecrate / Desecrate};
		\node[draw,rounded corners,fill=gray!15,below of=choosemap] (infuse) {Apply Map Rite: Enemies gain Holy / Daemonic Tag (x\%)};
		\node[draw,rounded corners,fill=gray!15,below of=infuse] (farm) {Run Map \& Farm Opposing Essence Drops};
		\node[draw,rounded corners,fill=gray!15,below of=farm] (altar) {Use Altar: Select Hero \& Attunement Direction};
		\node[draw,rounded corners,fill=gray!15,below of=altar] (pay) {Pay Essence Cost (Account-wide Storage)};
		\node[draw,rounded corners,fill=gray!15,below of=pay] (gain) {Gain Attunement Tier (+1 Step)};
		\path[->] (choosemap) edge (infuse)
		(infuse) edge (farm)
		(farm) edge (altar)
		(altar) edge (pay)
		(pay) edge (gain);
	\end{tikzpicture}
\end{center}

\subsubsection*{Description}

Each hero can be attuned towards exactly one of two opposing mythic alignments: \textbf{Holy} or \textbf{Daemonic}.
Attunement provides \textbf{tiered resistance} against one mythic damage type while simultaneously causing a \textbf{tiered vulnerability} against the opposing type.
Different heroes may specialize into different attunement directions.

\medskip
\noindent
\textbf{Core rule:}
\begin{itemize}
	\item High \textbf{Holy Attunement} $\Rightarrow$ high resistance vs.\ Holy damage \emph{and} high vulnerability vs.\ Daemonic damage.
	\item High \textbf{Daemonic Attunement} $\Rightarrow$ high resistance vs.\ Daemonic damage \emph{and} high vulnerability vs.\ Holy damage.
	\item Attunement is expressed in \textbf{fixed tiers} (not a continuously scaled value).
\end{itemize}

\begin{center}
	\begin{tabular}{c|l|l}
		\textbf{Tier} & \textbf{Holy} & \textbf{Daemonic} \\
		\hline
		1 & Blessed     & Tainted  \\
		2 & Sanctified  & Fallen   \\
		3 & Celestial   & Infernal \\
		4 & Seraphic    & Diabolic \\
	\end{tabular}
\end{center}

\noindent
\textbf{Essence-driven progression:}
\begin{itemize}
	\item Increasing attunement requires \textbf{Essences}. Each tier costs a \textbf{multiple} of the previous tier's cost.
	\item To gain \textbf{Holy Attunement}, the player must spend \textbf{Daemonic Essence} (dropped by enemies tagged \texttt{Daemonic}).
	\item To gain \textbf{Daemonic Attunement}, the player must spend \textbf{Holy Essence} (dropped by enemies tagged \texttt{Holy}).
\end{itemize}

\noindent
\textbf{Map rites (Consecration / Desecration):}
\begin{itemize}
	\item Once \textbf{Map Consecration} is researched, the player may choose per map whether to \textbf{Consecrate} (Holy) or \textbf{Desecrate} (Daemonic) it.
	\item Higher rite levels can be researched. At higher levels, a larger share of enemies is affected.
	\item If a map is \textbf{Consecrated}, then \textbf{x\%} of all enemies gain the \texttt{Holy} tag and their damage is converted to \textbf{Holy}.
	\item If a map is \textbf{Desecrated}, then \textbf{x\%} of all enemies gain the \texttt{Daemonic} tag and their damage is converted to \textbf{Daemonic}.
\end{itemize}

\noindent
\textbf{Intentional design decision (grind / roster play):}
To maximize attunement, the player is deliberately encouraged (and eventually forced) to \textbf{rotate between multiple heroes} and alternate farming of opposing essence types.

\subsubsection*{Execution}

To attune a hero, the player interacts with the \textbf{Altar} and selects a hero.
The Altar automatically displays the hero's current attunement tier and the essence costs for the next tier.

\begin{itemize}
	\item The player chooses the attunement direction (\textbf{Holy} or \textbf{Daemonic}). Only \textbf{one step} can be taken at a time.
	\item If sufficient essences are available, the player presses \textbf{Attune} to increase the tier by one.
	\item Essences are consumed on use. Essences are \textbf{account-wide} (not bound to a specific hero) and can be collected globally.
\end{itemize}
